### 20.2 闹钟响时氛围灯跟着闪

原来是 `r = blink ? 255 : 40`（1 秒一个周期、暗态还给 40），隔着透光壳几乎看不出在闪。
改成 2Hz 明灭、暗态全灭：

```c
if (alarmRinging) {                           // 闹铃：红灯跟着铃声闪（最高优先级）
  r = ((millis() / 250) & 1) == 0 ? 255 : 0;  // 250ms 一个半拍
}
```

`wsTask()` 10Hz 采样足够表达 2Hz 方波；`wsSend()` 内部有 `memcmp(c, wsLast, 6)` 去重，
不会因为 10Hz 调用就多推 RMT。仍然尊重 `cfg.rgbOn`：氛围灯总开关关了就不闪。

### 20.3 主按键＝全局静音（按"下"就静，不等抬手）

放在**按下沿**而不是短按释放沿，因为"立即静音"的语义是手一碰就静；
而且长按进配网、中按切 12/24 小时的时候也应当先把铃声掐掉。

```c
bool keySilence() {
  if (alarmRinging) { stopAlarm(true); return true; }        // 响铃：停 + 按设置排贪睡
  if (audioActive() || chimeSpeaking) { audioStop(); return true; }  // 试听/报时：只停，不排贪睡
  return false;
}
```

三个关键取舍：

- **试听不能排贪睡**：`stopAlarm(true)` 会按 `cfg.snoozeMin` 排下一次响铃。
  网页上试听一下铃声就凭空多出一次贪睡，是错的 —— 所以非响铃场景走 `audioStop()`。
- **必须清 `chimeSpeaking`**：`audioStop()` 已经顺手清掉。否则 `chimePump()` 会在 200ms 后
  把"被静音"误判成"打开失败"，串口打一行假的 `[CHIME] 打开失败，跳过`。
- **静音那一下不再顺带提亮**：`onShortPress()` 里用 `keySilenced` 闸住 `boostUntilMs`，
  保持"按铃即停"原有的手感，别让屏幕跟着炸亮。

### 20.4 顺手挖出两个真 bug（都是实测挖出来的，不是看代码看出来的）

**bug 1：按停之后同一分钟又响一遍。**
`handleAlarmSet()` 原来无条件 `lastAlarmKey[i] = 0`。这个键是"这一分钟已经响过"的凭据，
一清掉下一拍 `alarmDue()` 就重新匹配。于是闹钟正在响的那一分钟里，网页**哪怕只拨一下开关**
（时刻根本没动）也会让闹钟在按停后立刻复燃。用户 21:17 正在网页上调闹钟，正好撞上。

复现（修复前，串口原文）：

```
21:21:00  [ALARM] 到点 i=1 21:21 key=516801 → 响铃
21:21:00  /audiostop → ok                                   （停铃）
21:21:02  [ALM] set i=1 → 21:21 e=1 d=127 (h= m= e=1 d=)     （只拨开关，时刻没变）
21:21:02  [ALARM] 到点 i=1 21:21 key=516801 → 响铃          ← 同一分钟内又响
```

修法：只有**触发条件真的变了**（h/m/days 任一不同）才清去重键。同一脚本复测：

```
21:23:0x  /audiostop → 停
21:23:03  [ALM] set i=1 → 21:23 e=1 d=127 (h= m= e=1 d=)
停后 12 秒内的 [ALARM]/[KEY]： []
```

顺带把 `[ALM] set/del`、`[ALARM] 到点/贪睡到点` 这几行诊断打印留在固件里：
"闹钟表被谁改了"这种事，只靠读代码是查不出来的。

**bug 2：闹钟表被测试塞满，`/alarmadd` 静默失败。**
`MAX_ALARMS` 只有 5，而我前几轮端到端测试留下的临时闹钟（20:56/20:57/20:58/20:59/21:00，全部启用）
把表占满了，用户的 7:30 被挤出去。`/alarmadd` 返回 `full` 但脚本没检查返回值，
于是"设了 21:18 却不响"白等一轮。现在脚本一律**检查返回值 + 测完立刻删掉临时项并打印最终列表**。

### 20.5 v4.8.1：闹铃闪灯不受氛围灯开关约束

用户实测后指出：**「不管那个开关，氛围灯开关开或者关都不影响闹钟的氛围灯」**。
原实现里 `wsTask()` 开头就是 `if (!cfg.rgbOn) { wsSend(0,0,0,0,0,0); return; }`，
闹铃分支排在它后面，于是氛围灯开关一关，闹钟响的时候灯根本不亮。

修法：把闹铃分支提到 `cfg.rgbOn` 判断**之前**，直接 `wsSend` 后 `return`：

```c
static bool wsAlarmLit = false;
if (alarmRinging) {
  if (!wsAlarmLit) { wsAlarmLit = true;
    Serial.printf("[RGB] 闹铃闪烁开始（忽略氛围灯开关，rgbOn=%d）\n", cfg.rgbOn); }
  uint8_t v = ((millis() / 250) & 1) ? 0 : 255;   // 2Hz、暗态全灭
  wsSend(v, 0, 0, v, 0, 0);
  return;
}
if (wsAlarmLit) { wsAlarmLit = false; Serial.println(F("[RGB] 闹铃闪烁结束，回氛围灯设置")); }
if (!cfg.rgbOn) { wsSend(0, 0, 0, 0, 0, 0); return; }
```

为什么这么定：关灯是"夜里不想屋里有光"，不等于"响铃时也不想被提醒"。
闹铃闪灯是安全信号（一眼看出它在响），不该被日常夜灯开关连坐。配网蓝闪仍然受开关约束。

**同一个问题还有第二处**：`handleSave()` 结尾也有一句无条件 `lastAlarmKey[i] = 0`
（单闹钟时代留下的，那时闹钟就在首页上）。现在闹钟走 `/alarm` 独立接口，
`/save` 根本碰不到闹钟，这句只剩副作用 —— 你在网页上拨的正是氛围灯开关，走的就是 `/save`。
复现（修复前）：

```
21:28:00  [ALARM] 到点 i=1 21:28 → 响铃
21:28:01  /audiostop → 停
21:28:03  /save?vol=6 → ok                      （只改音量）
21:28:03  [ALARM] 到点 i=1 21:28 → 响铃          ← 复燃
```

删掉后同场景复测，响铃期间 `/save?vol=6` + `/audiostop`：

```
21:31:00  [ALARM] 到点 i=1 21:31 → 响铃
21:31:00  [RGB] 闹铃闪烁开始（忽略氛围灯开关，rgbOn=0）
21:31:02  /save?vol=6 → ok
21:31:02  /audiostop → ok
21:31:02  [RGB] 闹铃闪烁结束，回氛围灯设置
停后 12 秒内：无 [ALARM]
```

### 20.6 附：v4.7.9 拍手两声停铃（已删除，只留数据）

留档的原因是这些实测结论对以后任何"用这枚麦克风"的想法都有效：

- **只有绝对电平能分开拍手和铃声**（音量档 6，同一颗麦）：

  | | 峰值 | 峰均比 | 过零率 | 高频占比 |
  |---|---|---|---|---|
  | 铃声本身 | 66万~90万 | 2.24~3.77 | 79~460 | 48~172 |
  | 真人拍手 | 185万~440万 | 3.31~4.68 | 269~873 | 139~320 |

  后三项全部重叠，峰均比 / 过零率 / 高频占比只能当辅助门。阈值最终是
  `max(120万, 底噪×2.5)`；连续 25 秒纯响铃零误判，真闹钟端到端一次命中
  （间隔 322ms、峰值 4302552）。

- **`micMeasure()` 不能用于判据**：它把 128 个 int32 一起平均，而 I2S 立体声帧里
  只有一路有信号、另一路恒 0，rms 被稀释、峰均比虚高一倍 —— 而峰均比正是判据之一。
- **候选事件要按峰值取前 N 条**，按时间先到先占会被房间底噪（1~3 万）占满。
- **物理限制**：麦与喇叭同板只隔几厘米，音量 10 档时拍手要更响或更近；
  拍手和敲床板在单麦看来是同一件事，没有方向性。

### 20.8 v4.8.3：设置页右上角退出按钮

用户给了一张「门框 + 向右箭头」的图标，要求在网页设置端右上角加一个类似的按钮，
**点一下直接退到获取验证码的页面**。

- `/logout` 端点**原本就有**（GET/POST 都注册了，会 `authSessionDrop()` + 清 `sid` cookie），
  但只回一段 `text/plain: bye`，点了像没反应。现在补上 `Location: /login` + `303` +
  `Cache-Control: no-store`，浏览器直接跳到验证码页。
  用 303 而不是 302：GET/POST 统一转 GET，刷新不会重提注销。
- 首页 `PAGE_HTML` 头部加 `.topbar`：左边「小米闹钟」，右边一个 40×40 的白底圆角按钮，
  内联 SVG 画「门框 + 向外箭头」（`stroke:currentColor`，颜色 `#333348`，与截图接近）。
  用 `<a href="/logout">` 而不是 JS：没 JS 也能退，手机的返回键行为也正常。
- 跳到 `/login` 后**不会自动生成验证码**（v4.7.6 的规矩不变），用户还得点「获取验证码」。
  这正是"退到获取验证码的页面"的语义。

**v4.8.4 按用户反馈调整**：不要「小米闹钟」这个标题栏，把同一个退出按钮直接下移到

按钮改 `position:absolute;top:12px;right:12px`，卡片右侧留 58px 防止时间/日期钻到按钮底下。
按钮外观（白底圆角 + 深蓝门形箭头）和 `/logout` 行为都不变。

**v4.8.5 再调整**：用户指出手绘 SVG + 白底圆角方块在橙色卡上「太突兀」，要求照图抠图。

按亮度线性反推 alpha 保留抗锯齿，裁到 520×604 再等比缩到 34×40，
PNG 1047 B → base64 1396 字符内嵌进 `web_pages.h`（`data:image/png;base64,…`），
**不额外占 SPIFFS 文件**。同时删掉白底圆角与阴影，图标直接贴在橙色卡上，`opacity:.92`，按下 `.55`。

实测：页面 20,551 B；内嵌 PNG=True、旧 SVG 已移除、白底 CSS 已移除、`/logout` 仍 303→`/login`。

**v4.8.6 换高清原图**：用户又给了一张 1100×1100 的高清 JPEG（实心箭头 + 圆角门框），
替换掉之前从截图抠的 766×800 低清版。同样按亮度反推 alpha 抠图，裁到避开底部水印的
区域 `(185,245)-(925,860)`，缩到 44×36；PNG 1259 B → base64 1680 字符。

实测（curl，同一 cookie jar）：

```
1) 登录态 GET /        -> 200  退出按钮=True  icon=True
2) GET /logout        -> 303  Location=/login  Cookie=sid=; Max-Age=0
3) 退出后 /api/status -> 401 {"e":"auth"}
4) 退出后 GET /       -> 303  Location=/login
5) GET /login         -> 200  需要验证=True  获取验证码=True
```

原因是同一个 Python 脚本里先改 `handleLogout()`、再为升版本号**从磁盘重读并覆盖**了 `ino.ino`，
把前一步的改动冲掉了。编译和烧录都"成功"，只有接口实测能发现。以后同一脚本里改同一文件必须最后一次性写回。

## 19. v4.7.8 · 数码管"缺笔画"：静态画面 + 差量刷屏 + 单向写（2026-11-17 完成）

### 19.1 现象

用户贴了张照片：「这是什么情况？怎么数字还出现了缺笔画？」——屏上四个数字看起来是
`5 9 0 3`，但第一位那一格右侧空着、中间横也没有。

### 19.2 先把照片量清楚

按每位包围盒取七段亮度（PIL 取每段最亮 20% 像素的均值，规避相机曝光梯度）：

| 位 | a | b | c | d | e | f | g | 亮段 | 判读 |
|---|---|---|---|---|---|---|---|---|---|
| D1 | 232 | 66 | 246 | 244 | 23 | 244 | 67 | acdf | 像"5"少中横 / 像"C" |
| D2 | 237 | 237 | 241 | 238 | 16 | 243 | 239 | abcdfg | 9 |
| D3 | 233 | 236 | 237 | 239 | 242 | 82 | 121 | abcde(+f) | 0 |
| D4 | 241 | 235 | 216 | 239 | 15 | 20 | 243 | abcdg | 3 |

**D4=abcdg 与 `SEG_NUM[3]=0x4F`、D2=abcdfg 与 `SEG_NUM[9]=0x6F` 完全对上**，
说明测量几何是对的（D3 的 f 段因透视取样偏移漏检，不影响结论）。

### 19.3 关键一步：这个图案固件根本写不出来

`digit0`（小时十位）在固件里**只可能**被写成两个值：

```
SEG_NUM[0] = 0x3F = abcdef  ("0")
SEG_NUM[1] = 0x06 = bc      ("1")
```

而实测是 `0x2D = acdf`。对不出来 ⇒ 芯片里锁存的不是固件发过去的那一帧。

反推"原本该是哪一位"：
- 若本意是 `0`（0x3F）→ 要丢 **b、e 两位**
- 若本意是 `5`（0x6D）→ 只丢 **g 一位**

`0x6D → 0x2D` 恰好是 **清掉一个 bit（0x40）**，这是最典型的单比特传输错误。
而 `5 9 0 3` 正是四位验证码的样子，屏幕又**没有冒号**（验证码画面强制 `dispColon(false)`）
⇒ 照片是**验证码画面**，第一位本意是 "5"，丢了中横 g 段。

### 19.4 根因：错一帧，然后就再也不重写了

两条已知事实叠在一起才出问题：

1. **TM1652 只能写不能读**，写进去什么读不回来，一帧写歪了没有任何办法发现；
2. `tmFlush()` 有差量比较：`if (memcmp(frame, shown, 6) == 0) return;`

时钟画面每 500ms 翻一次冒号 ⇒ 帧内容一直在变 ⇒ 真的每 500ms 全量重写一次，
所以**时钟画面上错了也只错半秒**（这也是为什么平时从没见人提这问题）。

但**验证码画面是静态的**：`dispColon(false)` + 四位数字 30 秒不变 ⇒ 第一次写完之后
`memcmp` 一直相等 ⇒ **再也不重写**。那一帧只要歪一个 bit，错误就稳稳停在屏上
30 秒，正好够掏出手机拍张照。

产物实测支持这个解释：时钟画面 ≤0.5 秒就会自愈，用户不会去拍照；
能被拍到就只能是静态画面。

### 19.5 修法（两条，都很便宜）

```c
// ① 同一帧连写两遍：单比特错误在第二遍就被纠正，写歪概率≈0
for (int pass = 0; pass < 2; pass++) { waitCmd(); tmSend(TM1652_CMD_ADDRESS); … endCmd(); }
// ② 每 3 秒无条件重写一次：兜住"帧内容没变、但屏上是错的"这种差量比较看不见的情况
if (!force && millis() - lastForce >= 3000) { force = true; byTimer = true; }
```

代价：一帧 7 字节 ×11bit×49µs ≈ 3.5ms，连写两遍 7ms。
时钟画面 2 次/秒 ⇒ 约 1%（`loopUs` 158→209µs，`loopHz` 195→197，无感）；
静态画面只有 3 秒兜底那一次 ⇒ 0.23%。

### 19.6 实测（串口 + curl，不是推断）
新增 `disp{w,f}` 计数（真正上总线的帧数 / 其中由 3 秒兜底触发的次数），`/api/diag` 可读：

| 场景 | 6 秒内 | 说明 |
|---|---|---|
| 时钟画面（冒号在闪） | `w` +12，`f` +0 | 帧每 500ms 就变，兜底根本用不上 |
| 静态画面（段自检 8888） | `w` +2，`f` +2 | 兜底严格 1 次/3 秒，正是"帧不变"的场合 |

`loopHz=197`、`loopUs=147µs`（静态画面）、`loopMaxUs` 偶发 11.9ms（= 连写两遍那一下），
无性能退化。`/api/segtest` 走 `AUTH_ROUTE`，未登录仍返回 `401 {"e":"auth"}`。

### 19.7 新增：段自检接口

判断"到底是写歪了还是那颗 LED 坏了"，靠推理分不出来，让屏幕自己说：

```
GET /api/segtest?p=127&hold=600     # 四位全写 0x7F → 应该看到四个完整 8
GET /api/segtest?p=0                # 立刻退出自检，回时钟
```

`hold` 默认 20 秒、上限 600 秒（人要走到设备前面看一眼，20 秒太赶），到点自动回时钟，
免得忘了关、闹钟一直显示 8888。串口打 `[SEGTEST] 图案 0x..，保持 N 秒`。

**自检结果（2026-11-17 19:27）**：`?p=127` 之后屏幕显示**四个完整的 8**。
七段 × 四位全部正常 ⇒ **排除 LED 死段/虚焊**，确认是那一帧数据写歪 + 差量刷屏不重写。
（若当初是某段坏，`8888` 上会缺同一段；若是某位 grid 坏了，那一位会整体偏暗。）
自检关掉后 `/api/status` 回 `19:27`、`m24:1`，显示恢复正常。

## 18. v4.7.4~v4.7.7 · 网页访问验证：验证码只显示在闹钟屏幕上（2026-11-17 完成，全部实测）

### 18.1 为什么要做

用户提出：「网页端一直暴露在局域网里，不需要任何验证就能设置，是不是存在安全问题？」

现状（改之前）：**19 个端点全是 GET、无 token、不校验 Origin 也不校验 Host。**

| 风险 | 说明 |
|---|---|
| 同网设备/访客 | 连上同一个路由器的任何设备，打开浏览器就能改闹钟、清 WiFi、让喇叭出声 |
| 跨站盲打（CSRF） | 你在浏览器里打开过的恶意页面，写一句 `<img src="http://设备IP/resetwifi">`，浏览器就替你发了这个 GET |
| DNS rebinding | 恶意域名二次解析到设备 IP，绕过同源策略，`/api/diag` 的内容也能读走 |
| 配网热点 | `softAP` 无密码，同楼任何人连上 `XiaoClock` 就能把设备牵走 |

公网暴露另算：如果路由器做了端口转发或开了 UPnP，等于把这台零认证设备交给整个互联网。

### 18.2 方案：要求「物理在场」

加密码会回到「记密码」的老路，而且密码存在设备上也没比验证码强多少。
改成：

> 打开网页 → 闹钟的 4 位数码管显示 4 位随机数 → 输入它才能进设置页。
> 验证通过后数字立刻消失，屏幕回时钟。下次再进要重新来一遍。

**看得到这台机器的人，才知道那个数字。** 这就是物理在场证明。

4 位数码管正好放得下这个码，而且**关掉冒号**之后一眼就能和时间（HH:MM）分开。

### 18.3 实现要点

**① 验证码（`authPin` / `authPinMs` / `authNewPin()`）**

- `1000 + esp_random() % 9000` → 恒 4 位，没有前导零歧义；
- **必须主动获取**（v4.7.6 起）。打开验证页、未登录访问首页、提交过期码
  都**不会**生成验证码 —— 屏幕一动不动。只有点「获取验证码」（`GET /login?get=1`）才亮。
  这是整个功能最容易做错的地方：一打开页面就跳数字，误点链接、浏览器预取、
  自己随手开一下都会打扰闹钟；
- **屏幕亮 30 秒**，到点自己消失、屏幕回时钟（`renderDisplay()` 里优先级最高，
  仅次于响铃图标）；
- **两次获取之间隔 60 秒**（`AUTH_GET_COOL_MS`）。冷却剩余秒数由服务端渲染进
  页面的 `{{COOL}}`，**刷新页面也绕不过去**；
- **一次性**：登录成功立即 `authPin = 0`，屏幕当帧回时钟。

**② 会话（`authSessTok[4][33]`）**

```cpp
Set-Cookie: sid=<32 hex>; Path=/; HttpOnly; SameSite=Lax
```

- **不设 Max-Age** → 是 session cookie，关掉浏览器就没了；
- 服务端 4 个槽位，**120 秒没请求就当页面已关闭**并回收。
  这是「关掉网页就失效」的实际落点：浏览器不会在关标签时通知服务器，
  只能靠"不再有请求"来推断。页面开着时每秒 poll 一次，所以一直在续期。
- `SameSite=Lax` 顺便挡掉了跨站 `<img>` 借 cookie 发请求这条 CSRF 路径
  （Lax 下跨站子资源请求不带 cookie）。

**③ 端点守卫（`AUTH_ROUTE` 宏）**

```cpp
#define AUTH_ROUTE(uri, fn) server.on(uri, []() {            \
    if (reqFromAp() || authSessionValid()) { fn(); return; }  \
    authDeny(); })
```

- 页面类未认证 → `303 /login`；接口类（`/api/`）→ `401 {"e":"auth"}`。
  接口不跳转，否则网页 `fetch` 会拿到一段 HTML 再去 `JSON.parse`，报错更难查。
- **`Cookie` 头必须先用 `collectHeaders()` 声明**，否则 `server.header()` 读不到。

**④ 唯一的例外：从热点（192.168.4.x）进来的请求免验证**

那个热点只能靠长按主按键 3 秒亲手打开，「物理在场」已经证过了。
留这条也是怕死锁——设备装在高处、屏幕看不见时，至少还能长按进配网页把 WiFi 改掉。

**⑤ 防枚举**

- 同一个码最多错 5 次 → 作废并立刻换新码（屏幕上会看到数字变了）；
- 两次提交之间强制 3 秒冷却，脚本按不住 10000 种组合。


### 18.5 代价与残留风险（必须知道）

1. **人在外面就改不了设置**了。这是这个方案的必然结果，不是 bug。
2. **「关掉网页立即失效」做不到精确**。浏览器不会在关标签时通知服务器，
   所以实际是"页面 120 秒没有请求后失效" + session cookie（关浏览器即丢）。
   要绝对精确只能靠 `pagehide` + `sendBeacon`，但那会让**刷新页面也要重新验证**，不值得。
3. **`SameSite=Lax` 挡不住"点击恶意链接跳转"**：`<a href="http://设备IP/save?br=1">`
   属于顶级导航，会带 cookie。要根治得把写操作从 GET 改成 POST。
   下一步建议（还没做）：写操作改 POST + 校验 `Sec-Fetch-Site`。
4. **验证码是明文显示在屏幕上的**，站在设备旁边的人能直接读——这正是设计意图。

### 18.7 v4.7.5 的两处调整

第一版（v4.7.4）是「码 60 秒 + 验证页开着每 20 秒自动续期，上限 5 分钟」。
用户看过之后认为：

> 「屏幕上的码显示 60 秒太长了，可以设成 20 或 30 秒。
>  在输入框旁边加个刷新按钮，没显示的时候点一下立刻出一个。
>  设置闹钟一般都在手机上操作，没必要给它续期时间。」

改动：

1. `AUTH_PIN_MS` 60 秒 → **30 秒**（不做 20 秒：从看到数字到输完，30 秒留的余量更稳）；
2. 删掉整套续期（`AUTH_PIN_MAX_MS`、`authPinBorn`、`handleLogin` 里的 `keep` 分支、
   验证页里那个 20 秒 `setInterval`）。**屏幕不会再被长期占用**；
3. 验证页输入框右边加「刷新」（`<a href="/login?new=1">`），
   点一下整页重载并强制 `authNewPin("用户点了刷新")`。

副作用（可接受）：验证页打开后放着不管，30 秒后屏幕回时钟，得点刷新才能继续。
手机上这个场景几乎不存在——打开就是为了马上输。

### 18.8 v4.7.6：改成「主动获取验证码」

v4.7.5 还有个体验问题，是用户点出来的：

> 「这个逻辑是错的吧，不应该加刷新按钮，应该加一个获取验证码按钮。
>  因为只要你点开这个网页，它就会跳个验证码在屏幕上，这样很影响闹钟的体验。
>  要自己主动获取才会显示验证码。获取以后屏幕上显示一个倒计时 60 秒，
>  60 秒以后才能再获取。」

对。原来 `handleLogin()` 一进来就 `authNewPin()`，等于**任何人打开这一页，闹钟就跳数字**：
误点一个链接、浏览器预取、自己随手开一下都会亮一次。一个放在床头的钟，
被这样打扰是不能接受的。

改动：

1. **打开验证页不再生成码**。`handleLogin()` 只渲染页面；
2. 新增 `GET /login?get=1` —— **唯一**能生成验证码的入口，返回
   `{"ok":1,"cool":60,"pin":30}`；冷却中返回 `{"e":"wait","s":N}`；
3. `authDeny()` 和 `handleLoginPost()` 里原来"发现没码就补一个"的逻辑**全部删掉**，
   过期只提示「点获取验证码重新取」。**这是本次最关键的一处**——
   留着任何一处自动补发，屏幕都会自己跳；
4. 错 5 次不再自动换新码，而是作废 + 提示重新获取，并把获取冷却重新开始计时；
5. 按钮从「刷新」改成「获取验证码」，冷却期显示「N 秒后可再获取」并禁用；
6. 冷却剩余秒数由服务端渲染进 `{{COOL}}`，所以**刷新页面也绕不过 60 秒**。

屏幕上的时长仍是 30 秒（v4.7.5 定的），冷却 60 秒是"两次获取之间"的间隔 ——
两个数各管一件事，别混。若以后要把屏幕也亮 60 秒，改 `AUTH_PIN_MS` 一处即可。

## 17. v4.7.3 · 按键切 12/24 小时制与网页开关双向同步（2026-11-17 完成，全部实测）

### 17.1 现象与根因

用户反馈：「用按键设置 12 或 24 小时，和电脑网页端的设置按钮不同步。」

设备上**中按主按键（0.8~3 秒）**会把 `cfg.mode24` 取反，屏幕的小时格式立刻变；
但网页那个「24 小时制」开关**一直是打开页面那一刻的状态**，因为：

| 环节 | 原来 | 后果 |
|---|---|---|
| `#m24` 复选框 | 只在页面加载时由模板 `{{M24}}` 填一次 | 之后永远不再更新 |
| `poll()` 每秒做的事 | 只回写 `#t`（时间）与 `#d`（日期行） | 碰不到 `#m24` |
| `save()` 提交内容 | 无条件带上 `m24:$('m24').checked?1:0` | **拿着旧值提交** |

所以真正的坑不只是"显示不对"。用户按下按键切成 12 小时制之后，只要他再动**任何**一个
`onchange="save()"` 的控件（调亮度、改音量、拨氛围灯），网页就会把那个旧 `m24=1`
一起提交回去，**把按键的改动悄悄覆盖掉**——屏幕变回去了，人却以为是按键没生效。

### 17.2 三处改动（缺一不可）

**(1) `/api/status` 带上小时制真值**

状态接口原来不暴露 `mode24`，网页没有任何途径知道设备当前是什么制。

```json
{"t":"17:12","d":"… · 亮度 3","m24":1}
```

**(2) 网页每秒跟一次，只在真的不一样时才改写**

```js
function syncM24(v){
 var c=$('m24');
 if(!c||saving||v===undefined||v===null) return;
 var want=!!v;
 if(c.checked!==want){ c.checked=want; toast(want?'设备按键切换到 24 小时制':'设备按键切换到 12 小时制'); }
}
```

`saving` 是保存请求在路上的标志——这段时间内不能回写，否则会跟用户正在拨的手打架。

**(3) 用户没动过这个开关，就干脆不提交这个字段**

这是防覆盖的关键。`handleSave()` 本来就是「带了参数才改」，所以只要网页不发，
设备上按键设的值就一定保得住：

```js
if(m24Touch) p.set('m24',$('m24').checked?1:0);
```

`m24Touch` 由复选框自己的 `onchange="m24Touch=1;save()"` 置位，保存成功后清 0。

> 顺带踩到一个契约脚本的漏检：`verify_contract.py` 原来只从
> `new URLSearchParams({...})` 的对象字面量里抓 `key:`，改成 `p.set('m24',…)`
> 之后这个参数就"消失"在检查视野里了。已补一条 `\.set\(\s*'([a-z][a-z0-9]*)'` 规则，
> 现在仍是 **14 个参数对 14 个处理**。

**(4) 按键回调加一行日志**（证据留痕）

```cpp

```

## 16. v4.7.2 · 开机不再显示"另一个时区"的时间（2026-11-17 完成，全部实测）

### 16.1 现象与根因

用户反馈：「开机的时候有那么几秒会显示另一个时区的时间。」

根因是两个条件同时成立：

1. **复位不清 RTC 里的 epoch**。USB 复位 / 软件重启 / 看门狗都不会丢时间，
   `time()` 从上电起就返回一个"看起来有效"的值；
2. **时区在 RAM 里，复位即丢**。`configTime(8*3600, ...)` 设的是 TZ 环境变量，
   而它要等到联网之后才调用。这中间 `localtime_r()` 按 **UTC** 算 → 比北京时间早 8 小时。

串口里加一行日志就能直接看到（故意用 `gmtime_r` 打 UTC）：

```
[RTC] 复位后系统时间仍在：2026-11-17 08:55:35 UTC = 16:55:35 本地（不显示，等校时成功）
```

### 16.2 三处改动

**(1) 开机第一件事把时区钉死**

```cpp
static void fixTimezone() { setenv("TZ", "CST-8", 1); tzset(); }
```

> `TZ` 字符串里 `CST-8` 是「名为 CST、比 UTC 快 8 小时」，符号跟直觉相反，
> 写成 `CST+8` 会得到 UTC-8。这个字符串和 `configTime` 内部用的是同一个。

**(2) 校时成功之前一律不显示时间**

`getNow()` 里加一道闸：本次开机没校时成功（`lastSyncEpoch == 0`）就返回
`valid = false`，屏幕停在开机那套「等待表情」上，拿到网络时间再开始走字。

顺带消掉一个更隐蔽的坑：复位残留时间如果刚好撞上闹钟时刻，开机就会误响。
现在校时之前 `alarmTask()` / `chimeTask()` 全部不触发。

**(3) 30 秒兜底**

已经联网、但 SNTP 一直没回（路由器没外网）时，30 秒后允许使用复位残留时间：

```cpp
[RTC] 30 秒未校时成功，改用复位残留时间
```

否则屏幕会永远停在表情上 —— 那比"时间差几秒"更难理解。此时网页会标明：

```json
{"t":"16:39","d":"… · 未校时（复位残留时间） · 亮度 4"}
```

### 16.3 顺带修掉的假校时

`syncFromNtp()` 原来用 `time(nullptr) > 1700000000` 判断"SNTP 已经拿到时间"。
**这个判据在复位后是错的**：RTC 残留值天然满足它，于是刚开机就报"校时成功"，
网页显示"最近校时 0 分钟前（网络时间）"，其实一次 NTP 都没交互过。

改成只在真正收到 NTP 回包后才置位：

```cpp
static volatile bool sntpSynced = false;
static void onSntpSync(struct timeval *tv) { sntpSynced = true; }   // 回调里置位
...
if (!sntpSynced) return false;      // 没回包就不算校时
```

> 不能用 `sntp_get_sync_status()` 轮询代替：IDF 在置 `COMPLETED` 之后**马上又复位成
> `RESET`**，查到的概率很低。

### 16.4 校时提速：从 0.4~4.3 秒抖动到稳定 < 100ms

改完闸之后暴露一个新问题：**表情要亮到真正校上时为止**，而"发起→回包"实测在
0.4~4.3 秒之间乱跳（同一台设备、同一个路由器，连测三次都不一样）：

```
[NTP] 发起校时 @2247ms   →  [NTP] 收到回包 @5631ms    (3.4s)
[NTP] 发起校时 @1897ms   →  [NTP] 收到回包 @6225ms    (4.3s)
[NTP] 发起校时 @2402ms   →  [NTP] 收到回包 @3160ms    (0.8s)
```

排查过程（都不靠猜）：

| 试过的 | 结果 |
|---|---|
| 从电脑直接问 `203.107.6.88` 等 5 台服务器 | **20~47ms**，服务器没问题 |
| 把服务器换成 IP、去掉两次 DNS | 略好但仍在 0.4~2.1 秒抖动 |
| `sntp_restart()` 强制立刻发一次 | **没用**，甚至出现过 8 秒没回包 |
| 每 400ms 补发一次请求（共 6 次） | **更糟**，打乱了 SNTP 自己的状态 |
| **自己用普通 UDP 发一个 48 字节 SNTP 请求** | **首次即中，连上后 50~100ms** |

结论：延迟在 IDF SNTP 的**首次发包时机**（启动随机延迟 / 首次请求重传），
不在网络，也不在服务器，而且 sketch 里改不了。所以不等它：

```cpp
static bool ntpQueryOnce(const char *ipStr, uint16_t waitMs);   // 自建查询，收到就跑 settimeofday
```

* 只在首次校时时用，**最多 12 次、每次最多等 150ms**，没回就下一轮再试 ——
  网络长时间不通时不能一直占着主循环，否则刷屏会变卡；
* 成功一次就停，之后 6 小时一次的定期校时仍交给 IDF SNTP（它有平滑处理）；
* 第一个服务器直接给 IP（`203.107.6.88`，2026-11-17 用 dig 查的），省掉三次 DNS；
  后两个仍填域名，IP 万一失效还能靠域名兜住。

### 16.5 实测（复位三次，设备 192.168.8.129）

```
① [DISP] 显示等待表情 @716ms → [NTP] 自建查询拿到时间 @2013ms（第 1 次）→ [DISP] 开始显示时间 @2134ms
② [DISP] 显示等待表情 @716ms → [NTP] 自建查询拿到时间 @1969ms（第 1 次）→ [DISP] 开始显示时间 @1975ms
③ [DISP] 显示等待表情 @722ms → [NTP] 自建查询拿到时间 @5025ms（第 1 次）→ [DISP] 开始显示时间 @5126ms
```

任何时刻都不会显示未校时过的时间。

**兜底路径**（把服务器临时指向不可达地址模拟"路由器没外网"）：

```

```

注意 t≈30s 显示的 `16:39` 是**北京时间而不是 08:39** —— 这反过来证明 `fixTimezone()`
在完全没有网络的情况下也生效。

**回归**：首页与基线逐字节一致（忽略版本号与"最近校时 N 分钟前"）；`/api/status`、

### 15.2 启动：3 处改动，9.5 s → 2.5 s

**(1) SPIFFS 延后挂载 + NVS 一次性标记**

`SPIFFS.begin()` 是逐页扫描 3.24 MB 分区（12672 页 × 256 B），
**空分区也要 5.6 秒，与文件多少无关**。而 v4.7 的语音/铃声全部编进 flash 数组
（`chime_voice.h` / `ringtone_data.h`），文件系统只用于清理历史遗留文件。

```cpp
static void fsDeferredTask();   // loop 里跑：WiFi 连上后（12 s 兜底）才挂载
```

只挂一次没意义——每次开机都要 5.6 秒。所以清完历史文件就在 NVS 写一个
`fsclean=true`，之后开机直接跳过：

```
[FS] 历史文件已清理过，本次跳过挂载（省 5.6 秒）
```

顺带清掉了 v4.9 留下的 24 条真人录音（1.56 MB）和 `/kws` 目录。
**注意：SPIFFS 目录不能用 `SPIFFS.exists("/kws")` 判断（对目录永远返回 false）**，
必须 `SPIFFS.open(dir)` + `isDirectory()`，而且要先列出全部文件名再逐个删，
边遍历边删会让目录迭代器失效。

**(2) 定向关联：跳过 1~13 信道扫描**

实测关联一次要 3.2 秒。默认 `WiFi.begin(ssid, pass)` 会把 2.4G 的 13 个信道
逐个数一遍找同名 SSID。把上次连上时的信道和 BSSID 存进 NVS，下次直接对准它连：

```cpp
WiFi.begin(staSSID, staPass, (int32_t)apCh, apBssid, true);
```

```
[NET] 关联提示 信道 11  BSSID 08:9B:4B:12:66:17
[NET] 定向关联（跳过全信道扫描）
[NET] 关联耗时 1762ms
```

**兜底不能省**：路由器换信道 / Mesh 换节点时会连不上，所以 6 秒没连上就退回
普通扫描，并把 20 秒超时重新计时。宁可慢 3 秒，也不能连不上。

**踩过的坑（重要）**：退回时如果直接 `WiFi.begin(ssid, pass)`，会在串口看到

```
E (10258) wifi:sta is connecting, cannot set config
```

原因是 STA 还在 connecting 状态，驱动**拒绝**重新下发配置 —— 于是"以为退回了扫描，
其实什么都没发生"，只能干等 30 秒的掉线兜底重连。必须先停再起：

```cpp
WiFi.disconnect(false, false);   // 只断 STA，不擦 NVS、不关射频
delay(30);
WiFi.begin(staSSID, staPass);
```

这条路径用一个编译期钩子实测过（把信道故意指错）：

```cpp
#ifdef ASSOC_HINT_FORCE_BAD
  if (apCh) { apCh = (apCh == 1) ? 6 : 1; }
#endif
```

```
[NET] 关联提示 信道 1  BSSID ...
[NET] 定向关联（跳过全信道扫描）
[NET] 定向关联未成，退回全信道扫描
[NET] 已连接 Home  IP 192.168.8.129
[NET] 关联耗时 1638ms  信道 11
```

**(3) SNTP 快轮询**

`configTime()` 之后时间通常 100~300 ms 就有效了，原来 `ntpTask()` 固定 5 秒节流，
等于白等。改成"还没校上就 200 ms 轮询一次，校上以后回到 5 秒"：

```cpp
unsigned long gap = (ntpStarted && lastSyncEpoch == 0) ? 200UL : 5000UL;
```

### 15.3 主循环：164 Hz → 196 Hz（每轮 1212 µs → 155 µs）

分项耗时是量出来的，不是猜的（`/api/diag` 的 `prof` 字段）：

| 项 | 优化前 | 优化后 | 改动 |
|---|---|---|---|
| `web` | **1022 µs** | 65 µs | `server.enableDelay(false)` |
| `alarm` | 58 µs | 8 µs | `nowFast()` 时间缓存 |
| `chime` | 34 µs | 2 µs | `nowFast()` |
| `disp` | 55 µs | 47 µs | 不变（5 Hz 刷屏，差量比较） |

**(1) 主犯是 `server.enableDelay`**

`WebServer::handleClient()` 在没有请求时默认会 `delay(1)`（`_nullDelay = true`），
主循环每轮被白吃 1 毫秒 —— 占掉 loop 里 **84 %** 的干活时间。
关掉它空转立即返回；每轮末尾本来就有 `delay(5)` 让出 CPU，不会忙等。

**(2) `getNow()` 每秒被调几百次**

它内部是 `time()` + `localtime_r()`，实测 32 µs。alarm/chime/ws 的判断精度只到"秒"，
100 ms 缓存一次足够，最坏情况是整点报时晚 0.1 秒触发（报时窗口有 5 秒，无影响）。

```cpp
static const NowTime &nowFast();   // 100ms 缓存
```

### 15.4 首页：81 ms → 57 ms（固件侧 72 ms → 23 ms）

先量再改（`/api/diag` 的 `page` 字段，单位 µs）：

```
改前：拷贝模板 1.3ms / 18 次 replace 32.9ms / 发送 38.2ms  = 72ms
改后：单遍填表 5.7ms / 发送 17.5ms                        = 23ms
```

`String::replace()` 每次都从结尾把 17.6 KB 全文回扫一遍，18 次就是 18 遍。
改成单遍渲染：从头到尾只走一次，遇到 `{{NAME}}` 查表填值，其余原样拷贝。

```cpp
static void tplRender(String &out, const char *tpl, const TplVar *v, int n);
```

**验证方式**：改前改后各 curl 一份首页，`diff` 逐字节比对 —— 除"最近校时 N 分钟前"
这种随时间变化的字段外完全一致；再用 `/save` 改一组非默认值（亮度 6 / 音量 9），
确认回显正确、页面里没有残留 `{{...}}`。

剩下的 17.5 ms 是发 17.6 KB 的 TCP 时间（约 1 MB/s，受 RTT 与窗口限制），
不是固件算得慢，除非上 gzip 否则压不下去。

## 14. v4.6 · 射频自检：确认没有限功率（2026-11-17 完成，已实测）

### 用户疑问
「这个代码是之前项目移植过来的，之前的项目好像限制了信号功率。」

### 结论：限功率确实存在过，但**移植时就已经解除**
C3 原版 `MI-ALARM-ESP32C3/ESP32C3-PCB/ino/ino.ino:70` 是 `#define CFG_TX_DBM 6`
（自制板发射链供电/去耦不足，10dBm 以上波形压塌，临时限到 6dBm）。
S3 移植首版（commit `627bb9d`）已改成 **20dBm**，是 ESP32-S3 的硬件上限。

### 本版加固：把「关省电 + 满功率」合并并对齐时机
```cpp
static void applyRfPolicy(const char *when);   // esp_wifi_set_ps(NONE) + 20dBm + 读回校验
```
三处下发：开热点 / 关热点（切 mode 会重启 PHY）/ 配网连接。
**新增第四处**：`netTask()` 里 STA 连上之后再下发一次，防止 mode 切换把 PHY 打回默认。
串口每次都会打印实测值，不靠猜：
```
[RF] 配网连接 发射 20.0dBm(ok)  省电=关(ok)
[RF] 已连接 发射 20.0dBm(ok)  省电=关(ok)
```

### 新增 `GET /api/rf`
```json
{"rssi":-58,"ch":11,"tx_dbm":20.0,"ps":0,"st":3,"ip":"192.168.8.129","cfg_dbm":20}
```
`ps`：0=NONE（关省电）1=MIN_MODEM 2=MAX_MODEM。
排查「信号差」先看这两个数，能直接分开两类问题：

| 现象 | 根因 | 处理 |
|---|---|---|
| RSSI 正常但 ping 几百 ms、HTTP 偶发超时 | 省电（`WIFI_PS_MAX_MODEM`） | `applyRfPolicy()` 已强制 NONE |
| RSSI 很低（< -75）、丢包 | 天线/匹配/距离/信道拥堵 | 硬件侧，改固件无用 |

### 实测（设备 192.168.8.129，13:23~13:25）
| 项 | 结果 |
|---|---|
| 发射功率（读回） | **20.0 dBm**，`cfg_dbm=20`，设置返回 ok |
| 省电模式 | **0 = WIFI_PS_NONE** |
| RSSI / 信道 | **-58 ~ -59 dBm** / ch11（属于「良好」，不算弱） |
| ping 30 包 | 0% 丢包，min/avg/max = 2.2 / **5.4** / 23.9 ms |
| 开热点（AP_STA）时复测 | 仍是 20.0 dBm / ps=0，软 AP 没有把功率打回默认 |

**结论：固件没有在限制信号**，20dBm 已是上限、省电也关着。如果实际使用中仍觉得弱，
方向在硬件侧（天线净空、馈线、外壳屏蔽）或信道拥堵，不是这段代码。

### 14.1 网页头部显示实时信号质量（v4.7）
首页时间卡片第二行，在「亮度」**之前**插入信号分档与 dBm：

```

```

## 13. v4.5 · 16MB 分区 + 手机风格真实铃声（2026-11-17 完成，已编译/烧录/实测）

### 起因
用户指出「这块板子的 Flash 是 16M 的」，同时要求把 C3 时代移植过来的方波铃声
换成类似手机闹钟、有层次感的声音。

### 分区：8MB → 16MB
`esptool flash_id` 实测 `Detected flash size: 16MB`，但 `XIAO_ESP32S3` 板型菜单
只提供 8MB 方案，固件一直按 8MB 编，app 只有 3.34MB。`build.sh` 里用
`--build-property` 覆盖三项切到 `default_16MB.csv`：

| 分区 | 8MB 版 | 16MB 版 |
|---|---|---|
| app0 | 0x330000 (3.34MB) | **0x640000 (6.55MB)** |
| spiffs | 0x180000 (1.57MB) | **0x360000 (3.54MB)** |

`upload.maximum_size` 必须一起改，否则 arduino-cli 按 3.34MB 判超限。
烧录用 `sh flash.sh <port> --part`：只写 `0x0` 引导 + `0x8000` 分区表 +
`0xe000` boot_app0 + `0x10000` app，四段都落在 `0x9000`(NVS) 之外，
**Wi-Fi 与全部设置原样保留**（实测烧完直接 `WiFi=Home`）。
⚠️ 旧写法 `sh flash.sh ... | head -20` 会因为 SIGPIPE 在中途杀掉 esptool、
写出半截固件导致启动失败 —— 烧录日志要 `> 文件` 再 grep。

### 铃声：方波 → 6 段离线合成 WAV
方波只有基频和奇次谐波，听起来像老式电子表。手机铃声的「层次感」来自
多分音各自衰减 + 音量包络 + 混响，实时算吃 CPU，所以改成
`ringtone/generate.py` 在电脑上离线合成（numpy 加法合成 + 每分音独立指数衰减
+ 音头/音尾包络 + FFT 循环卷积混响 + tanh 柔和限幅），输出
22050Hz/16bit/单声道、8 秒、峰值统一 12000（与报时语音同电平），
全部写入同一个**环形缓冲**，尾巴绕回开头 → 循环无缝、接缝无「咔哒」。

| # | 名字 | 音色设计 |
|---|---|---|
| 0 | 晨曦 | 钟声琶音 C5-E5-G5-C6 + C3/G3 铺底 |
| 1 | 雷达 | 1720Hz 短脉冲四连打 + 108Hz 低频撞击，1 秒一组 |
| 2 | 木琴 | 木槌琶音（强 4 次分音）+ 低音木琴打底 |
| 3 | 广播 | 四短一长授时，风琴音色（带泛音）而非方波 |
| 4 | 信号 | E5-B5-E6 三音上行 + 长混响回声 |
| 5 | 渐强 | 铺底升温 + 加速上行钟声，越逼越紧 |

数据 2.02MB 编进 `ringtone_data.h`（`RING_0..RING_5`），走已有的
`playWavMem` → `AUDREQ_WAV_MEM` → `wavOpenMem` 从 flash 直读，
铃声靠 `loop=true` 到末尾自动绕回。方波旋律引擎
（`T0_F..T3_F` / `playMelody` / `audioTask`）整体删除。

### 实测（设备 192.168.8.129）
- 编译 `Sketch uses 4,955,361 bytes (75%)`，6.55MB 分区内；契约 18/18、14/14、10 宏全过。
- 分区表读回：`app0 0x10000 6400K / app1 0x650000 6400K / spiffs 0xc90000 3456K` ✓
- 烧录四段 `Hash of data verified`；开机 `[BOOT] XiaoMiClock v4.5 WiFi=Home`、NTP 成功、无 panic。
- 6 段铃声逐一试听，串口全部打印自己的资源名，`176398 帧`（8 秒），无打开失败。
- **循环**：闹钟 13:02 触发 → `[WAV] 播放(flash) 木琴 ... 循环`；麦克风实测在
  9.9s / 11.6s / 13.2s 仍是 25 万+ 峰值（远超单次 8 秒），点「立即静音」后掉到 5 万 → 循环与停止都正确。
- `/save?atone=5` 保存后网页读回 `value="5" selected`；旧接口 `/api/rings|sleep|sunrise|audio|wavprobe` 全 404。

### 产物
`build/XiaoMiClock_v4.5_esp32s3_{app,merged}.bin`；

## 12. v4.4 · 修复报时时段端点不报（2026-11-17 完成，已编译/烧录/实测）

用户反馈：设 7:00-22:00 时段时，7 点和 22 点不报。

**根因（两个叠加）**：
1. **小时错位**：报「X 点整」是在 `(X-1):59:55` 触发的，但旧代码拿**触发时刻** `t.h*60+t.m` 判断时段（=X-1 点 59 分），比被报的整点早 1 小时。报 7 点在 6:59:55 判断 `nowMin=419 < 420`，直接被挡掉。
2. **左闭右开**：`inChimeWindow` 用 `nowMin >= s && nowMin < e`，即使不错位也不含结束端点。

**修复**：新增 `shouldChimeHour(hour)`，在触发块内用**被报整点 nextHour**判断，改为**闭区间含两端**：
- `s<e`：`s <= hour <= e` → 7:00-22:00 报 7、8…22 共 16 个整点；
- `s>e`（跨零点）：`hour>=s || hour<=e` → 22:00-07:00 报 22、23、0…7；
- `s==e`：全天（保持默认行为）。

删掉旧的 `inChimeWindow`（已无调用者）；触发去重 `lastChimeKey` 不变。

**产物**：app SHA `a067ffb9…32e5`（2,838,624 B）/ merged `cd44b8cf…23c3`，归档 `firmware_backup/v4.4_*/`。

**实测**：编译 0 error、契约全过、`Hash verified` 烧录；网页设 07:00-22:00 读回两端均选中、固件显示 4.4；试听整句仍正常（hour_13 从 flash 播 39258 帧后正常结束）。
逻辑用脚本穷举验证：7:00-22:00 实报整点 = [7…22]（含两端）、跨零点 22:00-07:00 = [22,23,0…7]、全天 = 0…23，分钟去重仅首次触发。
**未做真机整点等待验证**（需等到 6:59:55 / 21:59:55），但完整触发链已穷举覆盖。

## 1. 这轮移植改了什么

| 模块 | C3 版 | S3 版 |
|---|---|---|
| 主控 | ESP32-C3，4MB Flash | XIAO ESP32-S3，8MB Flash（分区 `default_8MB`） |

## 7. 已知限制 / 装机前要确认

1. **没有 RTC**：断电后时间丢失，屏上会走等待动画，联网校时后才显示时间；断网期间闹钟不会响。这是硬件决定的，固件无解。要掉电走时只能加 DS1302/PCF85063 之类并留出 3 根 GPIO。
2. **GPIO1 = TM1652 单线数据线**，按你的确认处理。原始速记里的 `TM1652EN` 若是别的意思（比如电源使能），告诉我实际 SDA 脚位，`#define PIN_TM1652` 和接线表一起改即可。
3. **别叠 Sense 扩展板**：扩展板 SD 卡占 GPIO7/8/9（带上拉）、摄像头占 GPIO10，正好和本板 I2S 音频、彩灯打架。详见接线表第 6 节。
4. **GPIO0 是 strapping 脚**：上电瞬间按住 BOOT 键会进下载模式；跑起来后当主按键用没问题。
5. TM1652 与 WS2812B 都是 5V 器件、3.3V 数据，处在 VIH 边缘；换批次点亮异常时按接线表加电平转换或降压。
6. ICS-43434 的 L/R 选择脚要固定到 GND 或 VDD，别悬空；固件统计两个声道，接哪边都能读数。
7. `I2S_AMP_MAX = 10000` 是保守值，装机后按实际响度调；MAX98357 的 SD/GAIN 脚按 datasheet 接好，否则会表现为「完全无声」。
8. **Flash 实测 16MB，但固件仍按 `default_8MB.csv` 编译**：spiffs 分区只有 **1,438,481 字节**（约 1.4MB）。v4.1 内置 3 段 WAV 占 801,192 字节，自定义铃声上限 600KB，基本用满。要放长音频 / 语音模型再切 16MB 分区（`XIAO_ESP32S3` 板型菜单里没有 16MB 选项，需要自定义 partition CSV + `build.flash_size`）。
9. **首次开机有约 15 秒不响应 HTTP**：`SPIFFS.begin(true)` 首次会格式化分区（串口出现一次 `E (266) SPIFFS: mount failed, -10025`，是自动格式化的正常提示，不是故障），随后合成 3 段 WAV（实测 9.3s + 2.6s + 2.7s）。之后开机检测到文件已存在就跳过，2 秒内正常联网。
10. **上传 WAV 只接受 16bit PCM、单/双声道、8k~48kHz、≤600KB**。播放时线性插值重采样到 44.1kHz；首尾不为零的 WAV 循环播放时接缝可能有「咔」声，内置 3 段已做 50ms 首尾淡入淡出。

## 9. v4.1「唤醒体验」第 1 步（2026-11-15 17:46 完成）

> 这一节是**编译 → 烧录 → 真实串口日志 → curl HTTP 实测**全链闭合后的记录，不是设计稿。

### 9.1 范围与一个反直觉结论

**第 1 步不需要先切 16MB 分区。** 当前 `default_8MB.csv` 已有 `app0/app1` 各 3.3MB 和 1.5MB `spiffs`，v4.0 固件才约 1MB。切 16MB 要自定义 partition CSV + 改 `build.flash_size`（`XIAO_ESP32S3` 菜单里没有 16MB 选项），跟铃声播放毫无关系。**直接用现成的 spiffs 分区**就能放 2~3 段短铃声，把分区改造留到真需要长音频/语音模型时。

内置 WAV **不是**在电脑上生成再单独烧一个 spiffs 镜像，而是**首次开机由固件合成写入 SPIFFS**（`fsInit()` → `writeBuiltinRing()`）。理由：升级固件仍然只需烧一个 app @ `0x10000`，不会漏烧/错烧分区，也避免引入 mkspiffs 工具链。文件已存在就跳过。

### 9.2 铃声库与音频引擎

| 索引 | 名称 | 音源 |
|---|---|---|
| 0~3 | 上行三音 / 广播报时 / 电子急促 / 木琴 | 原方波旋律，**索引不变**，老 NVS 升级上来声音不变 |
| 4 | 晨光（柔和琶音） | `/rings/sunrise.wav` 内置合成 |
| 5 | 雨声 | `/rings/rain.wav` 内置合成 |
| 6 | 海浪 | `/rings/ocean.wav` 内置合成 |
| 7 | 自定义铃声 | `/rings/custom.wav` 网页上传，文件不存在时不出现在下拉里 |

内置 3 段统一 **22050Hz / 16bit / 单声道 / 6 秒 / 264,644 字节**（44 头 + 264,600 数据），带 50ms 首尾淡入淡出以便无缝循环。文件缺失或格式不支持时 `playTone()` 自动退回方波 0 号，保证闹钟不会「到点静音」。

`i2sFeedTask()` 仍是同一个 core 0 的 DMA 供给任务，现在有两套音源，通过 `audReq` 请求队列切换（**File/SPIFFS 操作只在音频任务里发生**，HTTP handler 只置标志，用 `portMUX` 临界区保证不会看到「新标志 + 旧路径」）：

- `AUD_TONE`：v4.0 的方波，逐样本 6ms 幅度渐变，`audioTask()` 在 loop 里推进音符。
- `AUD_WAV`：按块读 SPIFFS（1KB 缓冲）→ 线性插值重采样到 44100Hz → 音量淡变 → 写 I2S。支持单/双声道（双声道取平均）、8k~48kHz、按 RIFF 块遍历解析（能兼容带 LIST/fact 的非 44 字节头）、循环播放到文件尾自动 seek 回 data 块。

`/api/audio` 的 `mode`：`2` = WAV 流式播放（`pos` 是已送出的输出帧数）；`0` = 空闲或方波（此时看 `melody` 字段，`true` 表示方波旋律在跑）。

### 9.3 日出唤醒 / 助眠

- **日出**：只对「启用且今天在重复星期里」的闹钟生效，取最近一个；提前 `cfg.sunriseMin` 分钟开始，按 `progress²` 从暗红(12,0,0) → 橙(190,70,8) → 暖白(255,158,71) 渐亮。需要 `cfg.rgbOn=1`；响铃时让位给红闪。跨零点按 `d<0 → +1440` 处理。
- **助眠**：循环播放雨声/海浪（或「仅灯效」静音）+ 8 秒周期呼吸渐暗，整体亮度随剩余时间继续下压；到点自动停。闹钟到点、主按键短按、网页「停止助眠」都能结束。整点报时用 `audioActive()` 判断，不会打断助眠或试听。

### 9.6 实测暴露并修掉的问题

1. **STOP 只淡出音量、没结束播放**（实测发现）：`/audiostop` / 停止助眠后 `mode` 仍卡在 2、`pos` 继续涨，只是听不见。修复：`AUDREQ_STOP` 同时置 `wav.running=false`，让 `wavFill()` 淡出完成后关文件、回 `AUD_IDLE`。
2. **上传失败会删掉原有自定义铃声**（设计缺陷）：改为先写 `/rings/upload.tmp`，`wavCheck()` 通过后才 `remove(dst)` + `rename`，rename 不可用时逐块复制兜底；失败只删临时文件。
3. **`/api/sleep` 的 `min` 返回配置值而不是本次时长**：加 `sleepActualMin`，返回 `min`（本次实际）+ `cfgMin`（配置默认）。
4. 预防性修复（编译/推演阶段）：`struct WavState` 必须放在第一个函数之前，否则 Arduino 自动插入的函数原型引用未声明类型而编译失败；`wavNext()` 循环播放卡在数据块末尾时两轮重试；`playWav()` 切换前清 `toneAmp`，避免 WAV 结束后冒出残留方波；海浪包络用 `s*s` 代替 `powf(s,2)` 避免负数幂 NaN。
